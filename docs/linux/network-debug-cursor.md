# Network Debugging Guide for Docker Containers

This guide documents the systematic approach to diagnosing and resolving network connectivity issues in Docker containers, specifically focusing on package manager problems.

## Problem Scenario

**Issue**: CentOS 7 container cannot run `yum install` commands
**Symptoms**: 
- `yum repolist` shows 0 packages
- DNS resolution failures for mirrorlist.centos.org
- Repository connection errors

## Diagnostic Process

### Step 1: Verify Container Environment

```bash
# Check OS version and architecture
docker run -it centos:7 /bin/bash -c "cat /etc/os-release"
docker run -it centos:7 /bin/bash -c "uname -m && arch"
```

**Expected Output**:
```
NAME="CentOS Linux"
VERSION="7 (AltArch)"
ID="centos"
VERSION_ID="7"
```

**Key Finding**: Container is running aarch64 architecture, which is important for repository compatibility.

### Step 2: Test Package Manager Installation

```bash
# Check if yum is installed and working
docker run -it centos:7 /bin/bash -c "yum --version"
```

**Expected Output**:
```
3.4.3
  Installed: rpm-4.11.3-45.el7.aarch64 at 2020-11-13 01:55
  Built    : CentOS BuildSystem <http://bugs.centos.org> at 2020-09-30 15:29
```

### Step 3: Check Repository Status

```bash
# List available repositories
docker run -it centos:7 /bin/bash -c "yum repolist"
```

**Problem Indicators**:
```
Could not retrieve mirrorlist http://mirrorlist.centos.org/?release=7&arch=aarch64&repo=os&infra=container
error was 14: curl#6 - "Could not resolve host: mirrorlist.centos.org; Unknown error"
repo id                                           repo name                                           status
base/7/aarch64                                    CentOS-7 - Base                                     0
extras/7/aarch64                                  CentOS-7 - Extras                                   0
updates/7/aarch64                                 CentOS-7 - Updates                                  0
repolist: 0
```

**Analysis**: All repositories show 0 packages, indicating connectivity issues.

### Step 4: Test Basic Network Connectivity

```bash
# Test internet connectivity
docker run -it centos:7 /bin/bash -c "ping -c 3 8.8.8.8"
```

**Expected Output**:
```
PING 8.8.8.8 (8.8.8.8) 56(84) bytes of data.
64 bytes from 8.8.8.8: icmp_seq=1 ttl=63 time=114 ms
64 bytes from 8.8.8.8: icmp_seq=2 ttl=63 time=40.2 ms
64 bytes from 8.8.8.8: icmp_seq=3 ttl=63 time=36.8 ms
```

**Result**: Basic internet connectivity works, so the issue is DNS-related.

### Step 5: Check DNS Configuration

```bash
# Check DNS resolver configuration
docker run -it centos:7 /bin/bash -c "cat /etc/resolv.conf"
```

**Typical Output**:
```
# Generated by Docker Engine.
nameserver 192.168.65.7
```

**Analysis**: Docker's internal DNS server might not be resolving external domains properly.

### Step 6: Test DNS Resolution

```bash
# Test DNS resolution (if nslookup is available)
docker run -it centos:7 /bin/bash -c "nslookup mirrorlist.centos.org"
# Or test with curl
docker run -it centos:7 /bin/bash -c "curl -I http://mirrorlist.centos.org"
```

## Root Cause Analysis

### Primary Issues Identified

1. **DNS Resolution Failure**: Container cannot resolve `mirrorlist.centos.org`
2. **Architecture Compatibility**: aarch64 architecture has limited repository support
3. **CentOS 7 EOL**: CentOS 7 reached End of Life on June 30, 2024
4. **Repository Unavailability**: Official aarch64 repositories are no longer maintained

### Architecture-Specific Problems

The container is running on aarch64 architecture, but:
- CentOS 7 aarch64 repositories are deprecated
- Many mirror sites don't maintain aarch64 packages for EOL versions
- Official CentOS mirrors have limited aarch64 support

## Solutions

### Solution 1: Fix DNS Resolution (Temporary)

```bash
# Update DNS configuration
docker run -it centos:7 /bin/bash -c "
echo 'nameserver 8.8.8.8' > /etc/resolv.conf
echo 'nameserver 8.8.4.4' >> /etc/resolv.conf
cat /etc/resolv.conf
"
```

### Solution 2: Use Alternative Mirror Sources

```bash
# Configure alternative repositories
docker run -it centos:7 /bin/bash -c "
# Backup original configuration
cp /etc/yum.repos.d/CentOS-Base.repo /etc/yum.repos.d/CentOS-Base.repo.backup

# Use Vault repositories
cat > /etc/yum.repos.d/CentOS-Base.repo << 'EOF'
[base]
name=CentOS-\$releasever - Base
baseurl=http://vault.centos.org/7.9.2009/os/\$basearch/
gpgcheck=1
gpgkey=file:///etc/pki/rpm-gpg/RPM-GPG-KEY-CentOS-7

[updates]
name=CentOS-\$releasever - Updates
baseurl=http://vault.centos.org/7.9.2009/updates/\$basearch/
gpgcheck=1
gpgkey=file:///etc/pki/rpm-gpg/RPM-GPG-KEY-CentOS-7

[extras]
name=CentOS-\$releasever - Extras
baseurl=http://vault.centos.org/7.9.2009/extras/\$basearch/
gpgcheck=1
gpgkey=file:///etc/pki/rpm-gpg/RPM-GPG-KEY-CentOS-7
EOF

# Clean cache and test
yum clean all
yum makecache
"
```

### Solution 3: Use Modern Alternatives (Recommended)

#### Option A: Rocky Linux 8/9 (CentOS Successor)
```bash
# Rocky Linux 8 with working package manager
docker run -it rockylinux:8 /bin/bash -c "dnf --version && dnf repolist"
```

#### Option B: CentOS Stream 8/9
```bash
# CentOS Stream (if available)
docker run -it centos:stream8 /bin/bash -c "dnf --version"
```

#### Option C: AlmaLinux 8/9
```bash
# AlmaLinux (another CentOS successor)
docker run -it almalinux:8 /bin/bash -c "dnf --version"
```

### Solution 4: Disable Problematic Repositories

```bash
# Disable failing repositories temporarily
docker run -it centos:7 /bin/bash -c "
yum-config-manager --disable base
yum-config-manager --disable updates
yum-config-manager --disable extras
yum install -y wget
"
```

## Prevention Strategies

### 1. Use Supported Distributions
- Avoid EOL (End of Life) distributions
- Prefer actively maintained alternatives
- Check architecture compatibility

### 2. Container Best Practices
```bash

# Check image metadata
docker inspect rockylinux:8 | grep -i arch
```

### 3. Network Configuration
```bash

```

## Common Error Messages and Solutions

### "Could not resolve host"
**Cause**: DNS resolution failure
**Solution**: Update DNS configuration or use different DNS servers

### "HTTP Error 404 - Not Found"
**Cause**: Repository URL is invalid or architecture not supported
**Solution**: Use alternative repositories or different distribution

### "No more mirrors to try"
**Cause**: All configured mirrors are unavailable
**Solution**: Update repository configuration or use different base image

### "repodata/repomd.xml not found"
**Cause**: Repository structure has changed or is unavailable
**Solution**: Use Vault repositories or switch to supported distribution

## Conclusion

The CentOS 7 aarch64 container issue was caused by a combination of:
1. DNS resolution problems
2. Architecture-specific repository limitations
3. End-of-life status of CentOS 7

The most effective solution is to migrate to a supported distribution like Rocky Linux 8/9, which provides better aarch64 support and active maintenance.

## Network Layer Debugging Guide

### Understanding Network Layers and Protocols

The OSI model provides a framework for understanding network communication. Each layer has specific protocols and debugging techniques:

#### Layer 1: Physical Layer
- **Purpose**: Physical transmission of data
- **Protocols**: Ethernet, WiFi, Fiber
- **Debug Tools**: 
  ```bash
  # Check physical interface status
  ip link show
  ethtool eth0
  ```

#### Layer 2: Data Link Layer
- **Purpose**: Error detection, MAC addressing
- **Protocols**: Ethernet, PPP, Frame Relay
- **Debug Tools**:
  ```bash
  # Check MAC addresses and ARP table
  ip neigh show
  arp -a
  # Monitor layer 2 traffic
  tcpdump -i eth0 -e
  ```

#### Layer 3: Network Layer (IP Layer)
- **Purpose**: Routing, logical addressing
- **Protocols**: IP, ICMP, ARP
- **Debug Tools**:
  ```bash
  # Test IP connectivity (what ping 8.8.8.8 does)
  ping 8.8.8.8
  ping -c 4 8.8.8.8
  
  # Check routing table
  ip route show
  route -n
  
  # Trace network path
  traceroute 8.8.8.8
  mtr 8.8.8.8
  ```

#### Layer 4: Transport Layer
- **Purpose**: End-to-end communication, reliability
- **Protocols**: TCP, UDP
- **Debug Tools**:
  ```bash
  # Check active connections
  netstat -tuln
  ss -tuln
  
  # Monitor TCP connections
  tcpdump -i any tcp port 80
  ss -tuln | grep :80
  ```

#### Layer 5-7: Session, Presentation, Application Layers
- **Purpose**: Application-specific protocols
- **Protocols**: HTTP, HTTPS, DNS, FTP, SSH
- **Debug Tools**:
  ```bash
  # Test HTTP connectivity
  curl -I http://example.com
  wget --spider http://example.com
  
  # Test DNS resolution
  nslookup example.com
  dig example.com
  host example.com
  
  # Test specific ports
  telnet example.com 80
  nc -zv example.com 80
  ```

### Layer-by-Layer Debugging Process

#### Step 1: Physical and Data Link Layers
```bash
# Check if network interface is up
ip link show
# Should show: state UP

# Check for link errors
ethtool -S eth0 | grep -i error
# Look for: rx_errors, tx_errors, dropped

# Check ARP table
ip neigh show
# Should show gateway and other local devices
```

#### Step 2: Network Layer (IP)
```bash
# Test basic IP connectivity
ping 8.8.8.8
# Success means: IP layer is working

# Check routing
ip route show
# Should show default gateway

# Test to gateway
ping $(ip route | grep default | awk '{print $3}')
```

#### Step 3: Transport Layer
```bash
# Test TCP connectivity
telnet 8.8.8.8 53
# Success means: TCP layer is working

# Test UDP connectivity
nc -u -v 8.8.8.8 53
# Success means: UDP layer is working
```

#### Step 4: Application Layer
```bash
# Test DNS (UDP port 53)
nslookup google.com
dig google.com

# Test HTTP (TCP port 80)
curl -I http://google.com

# Test HTTPS (TCP port 443)
curl -I https://google.com
```

### Common Network Issues by Layer

#### Layer 1-2 Issues
- **Symptoms**: No network connectivity at all
- **Causes**: Cable unplugged, interface down, driver issues
- **Debug**:
  ```bash
  ip link show
  dmesg | grep -i network
  ```

#### Layer 3 Issues
- **Symptoms**: Can't reach specific IPs, routing problems
- **Causes**: Wrong IP configuration, routing table issues
- **Debug**:
  ```bash
  ip addr show
  ip route show
  ping 8.8.8.8
  ```

#### Layer 4 Issues
- **Symptoms**: Can ping but can't connect to services
- **Causes**: Firewall blocking ports, service not running
- **Debug**:
  ```bash
  telnet target_host port
  netstat -tuln | grep port
  iptables -L
  ```

#### Layer 5-7 Issues
- **Symptoms**: Can connect but application doesn't work
- **Causes**: DNS problems, application errors, protocol issues
- **Debug**:
  ```bash
  nslookup domain.com
  curl -v http://domain.com
  ```

### Why `ping 8.8.8.8` Tests IP Layer

The `ping` command specifically tests the **Network Layer (Layer 3)** because:

1. **Uses ICMP Protocol**: ICMP is a Layer 3 protocol that sits on top of IP
2. **Bypasses Higher Layers**: Doesn't require DNS, HTTP, or application protocols
3. **Tests IP Routing**: Verifies that IP packets can be routed to the destination
4. **Tests Basic Connectivity**: Confirms the network stack can send/receive packets

```bash
# What ping 8.8.8.8 actually does:
# 1. Creates ICMP Echo Request packet
# 2. Wraps it in IP packet with destination 8.8.8.8
# 3. Sends through network stack
# 4. Waits for ICMP Echo Reply
# 5. Measures round-trip time

# Equivalent manual test:
tcpdump -i any icmp and host 8.8.8.8
ping 8.8.8.8
```

### Network Troubleshooting Decision Tree

```
Network Problem?
├── Can ping 8.8.8.8?
│   ├── Yes → IP layer works
│   │   ├── Can resolve DNS?
│   │   │   ├── Yes → Test application layer
│   │   │   └── No → DNS problem (Layer 7)
│   │   └── Can connect to specific port?
│   │       ├── Yes → Test application protocol
│   │       └── No → Transport layer problem (Layer 4)
│   └── No → IP layer problem (Layer 3)
│       ├── Check routing table
│       ├── Check IP configuration
│       └── Check physical connectivity
```

为什么要 ping 8.8.8.8？

ping 8.8.8.8 是一个分层的网络诊断方法：

```
应用层 (HTTP, DNS, yum) ← 这里出问题了
传输层 (TCP/UDP)
网络层 (IP) ← ping 8.8.8.8 测试这一层
链路层 (Ethernet)
物理层
```

网络分层解释：

1. 网络层 (IP层)：负责主机到主机的通信，通过IP地址寻址
   · ✅ ping 8.8.8.8 测试这一层 → 能通说明IP包能出去也能回来
   · 这证明：网卡、路由、防火墙（基础规则）都正常
2. 传输层 (TCP/UDP层)：负责端到端的通信，通过端口号区分服务
   · 需要测试：TCP连接是否正常
3. 应用层：具体的应用程序协议（DNS、HTTP、HTTPS）
   · ❌ 你的问题出在这一层：DNS解析失败

现在我们知道：网络层是通的，但应用层有问题

如何进一步诊断？（用容器内已有的工具）

既然 ping 8.8.8.8 通，但 yum install 失败，我们可以这样排查：

```bash
# 1. 查看当前的DNS配置（基础镜像应该有cat命令）
cat /etc/resolv.conf

# 2. 测试DNS服务器是否可达（用ping测试DNS服务器的IP）
ping -c 4 8.8.8.8       # Google DNS
ping -c 4 114.114.114.114 # 国内DNS

# 3. 测试端口连通性（用telnet或简单的TCP测试）
# 如果没有telnet，可以用bash内置方法：
timeout 2 bash -c "</dev/tcp/8.8.8.8/53" && echo "DNS端口53可达" || echo "DNS端口53不可达"
timeout 2 bash -c "</dev/tcp/mirrorlist.centos.org/80" && echo "HTTP端口80可达" || echo "HTTP端口80不可达"

# 4. 手动解析DNS（用getent如果可用）
getent hosts google.com

# 5. 检查路由表（如果有route命令）
route -n
# 或者看 /proc/net/route
cat /proc/net/route
```

```bash
# 测试其他常用网站的80端口
timeout 2 bash -c "</dev/tcp/www.baidu.com/80" && echo "百度HTTP可达" || echo "百度HTTP不可达"
timeout 2 bash -c "</dev/tcp/www.163.com/80" && echo "网易HTTP可达" || echo "网易HTTP不可达"
```

- ICMP协议：被防火墙阻挡（ping使用ICMP协议）
- TCP协议：80/443端口不可达，说明HTTP/HTTPS也被阻挡

```
协议/端口 状态 说明
DNS (UDP 53) ✅ 可用 域名解析正常
ICMP ❌ 被阻 ping命令失败
HTTP (TCP 80) ❌ 被阻 网页访问失败
HTTPS (TCP 443) ❌ 被阻 加密网页访问失败
```
